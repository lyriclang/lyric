TCP for tasks: listen/accept on the server side, connect on the client's, readSome/write on both, every waiting form yielding to the scheduler instead of blocking the thread.

The silent forms answer whether (null/false); the OrThrow twins say why with an IoError, from the same implementation. readSome folds three truths into one answer: bytes are bytes, an EMPTY array is the peer being done (EOF), and null is a failure.

Packet struct

pub struct Packet

One received datagram: its payload, and who sent it — the address sendTo answers to.

UDP has no EOF, so an EMPTY payload here is a real (empty) packet, not an end — the one place this module's bytes mean something different than readSome's.

bytes: uint8[]

The payload, complete: a datagram arrives whole or not at all.

host: string

The sender's address, as the receiving socket saw it.

port: int

The sender's port.

readSome function

pub fn readSome(socket: Socket, max: int): ?uint8[]

Waits for bytes and reads up to max of them. Three truths in one answer: bytes are bytes, an EMPTY array is the peer being done (EOF), and null is a failure — readSomeOrThrow says which failure.

A max of zero or less PANICS: an empty answer already means EOF, so there is no honest value to hand back for it.

receiveFrom function

pub fn receiveFrom(socket: UdpSocket, max: int): ?Packet

Waits for one datagram and answers it whole, with its sender. A payload longer than max is CUT to it — datagrams do not queue their remainder. null is a failure; receiveFromOrThrow says which. An empty payload is a real packet: UDP has no EOF.

A max of zero or less PANICS. It would otherwise cut the datagram to one byte and throw the rest away, which is the cutting rule above turned into silent data loss.
